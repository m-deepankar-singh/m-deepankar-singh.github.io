Case study № 1 · AWS Neuron NxDI

Bringing Qwen 3.6’s hybrid DeltaNet architecture to AWS Trainium — with no existing NxDI reference implementation

lead author · upstream contribution · PR #173 · +58,329 / −300 across 102 files · validated on trn2.3xlarge, TP=4, LNC=2, Neuron SDK 2.29

Qwen 3.6-27B is a hybrid: 48 Gated DeltaNet recurrent layers interleaved with 16 GQA attention layers. NxDI had no serving path for that shape, and no Trainium reference implementation existed to port from. This is the account of building one: three custom NKI kernels, a numerical failure that passed every unit test and still emitted garbage end-to-end, and a caching design that had to teach vLLM what recurrent state is.

1Why a hybrid breaks the framework

A conventional decoder-only port can assume every layer owns KV state, that cached state is indexed by token slots, and that restoring a prefix means restoring KV. Qwen 3.6-27B violates all three. Its 64 layers repeat a 3 DeltaNet + 1 GQA pattern sixteen times. Only the 16 GQA layers keep a token-length KV cache; the 48 DeltaNet layers carry a fixed-size recurrent matrix and a convolution tail instead — state that represents a specific prefix boundary, not per-token block data.

Restore attention KV without restoring the matching recurrent and convolution state and the model silently changes its output. Nothing crashes. That asymmetry — three state families that must agree, in a framework built for one — shaped every design decision that followed.

Three model-level details caused real failures on top of that: the GQA q_proj interleaves query and output-gate values that must be split during weight conversion; DeltaNet's internal RMSNorms use the ordinary convention while most Qwen norms use norm(x) · (1 + w); and only 64 of each 256-dimensional head is rotary, so stock fused kernels that assume full-head RoPE can't be used unchanged.

2Three kernels for DeltaNet

DeltaNet's recurrence maps onto nothing in Neuron's kernel library, so I wrote three custom NKI kernels: a recurrent decode kernel running the one-token form, a per-chunk reference kernel that computes the chunked parallel recurrence one chunk at a time and served as the correctness oracle, and a fused context-encoding kernel for prompt ingestion. The fused variant is the interesting one: it keeps the recurrent state resident in SBUF (on-chip memory) across chunks and computes cumulative decay in-kernel, rather than round-tripping state through HBM between chunks.

The first correct hardware baseline — BF16, 64K context, chunked prefill, FP32 recurrent state — held 149.5–149.7 prefill tok/s flat from 1K through 64K tokens. Slow, but flat: the implementation was no longer degrading with cumulative position. That mattered more at the time than raw speed, because a throughput curve that decays with context is a correctness signal, not a performance one.

3The failure that only became visible end-to-end on hardware

The fused kernel repeatedly emitted !!!! or incoherent text while simpler chunked paths worked. Three candidate causes had to be separated: a wrong DeltaNet formula, an unstable triangular solve, or wrong state carry across successive kernel calls.

It was the solve. An unstable Neumann-style correction measured only 0.9156 cosine against reference in BF16 — good enough to compile, load, return finite logits, and produce garbage. The fix was a direct blocked triangular solve in which each diagonal block of (I − A) is inverted by power doubling. Because the block is strictly lower-triangular and therefore nilpotent, that construction is exact — not an infinite-series approximation. Paired with FP32 recurrent state, quality probes at 762, 1K, 4K, 16K and 64K became coherent.

The solve is expensive. Replacing it with the identity matrix — deliberately breaking the model — cut 16K TTFT from ~36.9s to 14.6s, removing about 61% of baseline TTFT and roughly 91% of all removable recurrent-core time. That is the price of correctness here, measured precisely, and it was worth paying: a fast kernel that emits garbage has a throughput of zero.

4Optimization by falsification

Most of the speed work was rejecting plausible ideas with measurements instead of promoting them on intuition. Capping the attention cache at 4,096 tokens was 1.04× faster and changed generated tokens — not worth it. An eight-block Vector-Engine solve compiled and produced coherent text at 102 tok/s, roughly 4× slower, because it traded Tensor Engine work for row shuffles. Duplicating the first four DeltaNet calls implied only a 4.7% extrapolated cost from per-call dispatch — which said a two-week head-batching rewrite was not yet justified.

The most instructive negative result was a valid algebraic simplification. Refactoring the solve as N·(v−k·S) rather than N·v − (N·k)·S matched the baseline to 2.3e-10 max absolute difference, hit 0.9997 average logit cosine, and reproduced downstream MMLU and GSM8K predictions exactly, 40/40 and 20/20 — and then measured 429.29 vs 429.31 tok/s in production vLLM. Correct, and worth nothing once the full graph was compiled and scheduled. Knowing which is which before committing weeks to it is the actual skill.

5Teaching vLLM what recurrent state is

The first hybrid cache manager was static and batch-row-oriented — fine for local generation, incompatible with everything that defines production serving: block KV layout, continuous batching, slot mapping, prefix caching. The production design treats DeltaNet state as a prefix-boundary checkpoint, and a prefix is reusable only at the intersection of three independent hits:

usable_prefix = min(
attention_KV_hit,
GDN_recurrent_checkpoint_hit,
GDN_convolution_checkpoint_hit,
request_prompt_length)

Getting there meant fixing a long tail of things that only surface under real scheduling: vLLM was counting KV for all 64 layers instead of 16 (a 64 GiB phantom estimate); warm suffix requests arrived without the full prompt DeltaNet needs to restore context; generated tokens polluted the recorded prefix length during decode; async checkpoint commits could outlive their slots; and incomplete prefill rows were being sampled, appending dummy token 0 — which renders as !!!! and which the validator initially accepted, because token 0 is technically in vocabulary range.

With that in place, an exact-repeat gate on a 10,601-token prompt went from 26.58s cold to 3.07s warm with identical output. Partial-prefix and cross-prefix cases reproduce exactly too — warm results equal cold results, token for token.

26.6 s → 3.1 s cold → warm, 10.6K prompt · byte-identical output · 8.7×

6FP8, segmented HBM, and the 256K wall

The 96 GiB of accelerator memory on a trn2.3xlarge is physically four 24 GiB banks, and that distinction cost weeks. A graph fits in aggregate and still fails because one bank can't allocate another aligned 2 GiB scratchpad. Long context was a memory-layout problem before it was a compute problem.

Extending FP8 past the MLP path meant transforming scale tensors identically to weights — splitting interleaved Q and gate scales, concatenating fused QKV scales, reordering DeltaNet scales for tensor parallelism (via an int8 view, because PyTorch refuses to concatenate float8_e4m3fn directly). Then the compiler started failing on specific square bucket shapes, which forced a deliberately non-square CTE ladder — 512, 768, 1,536, 3,072 — plus sparse bucket pairs, because NxDI assumed a rectangular Cartesian product and was compiling combinations that were useless or crashed outright.

Two more walls stood in front of 256K. The stock segmented context-encoding kernel asserts head_dim ≤ 128; Qwen uses 256. The custom replacement splits Q/K into two 128-wide tiles and accumulates before softmax — and in its first form blew past SBUF with a 128×402,724 allocation, which a windowed rewrite cut to 31,360, under the 32,767 limit. Then the compiled 256K graph crashed on an out-of-bounds DMA: the final active chunk was only 768 tokens, but the loop read six full sections and walked off the block table. Padding the internal table to 1,036 entries made the overreads resolve to block zero.

There was also a genuine off-by-one worth remembering: vLLM reserves a null block, so a 1,024-user-block configuration needs 1,025 physical blocks compiled into the artifact.

7What the numbers show

The current publishable artifact is a coherent 256K-capable native-chunk build using selective FP8 weights, BF16 KV and LM head, and FP32 DeltaNet recurrent state. Against an internal baseline of 623.0 tok/s it measured 2,394.6 prefill tok/s at 16K context — a 3.84× speedup — with TTFT of 6.84s, and sustained 1,029.2 tok/s out to 242,864 usage-accounted prompt tokens.

The decode curve is the result I find most convincing, because it isn't a speed number at all — it's an architectural signature. Across a 6,000× increase in prompt length, from 11 tokens to 65,506, decode throughput falls about 3%. That is exactly what a 48/16 hybrid should do: three quarters of the layers hold fixed-size recurrent state, so growing context can only load the remaining sixteen.

8What is validated, and what isn't

Against Hugging Face greedy decoding, the implementation matched 156 of 160 generated token positions (97.5%) across ten prompts, with nine of ten cases exact for sixteen tokens. Below that sit 57 CPU unit tests across config, weight conversion, hybrid cache and decay; eight device integration categories; and checked-in prefix-cache exactness gates.

Being precise about scope matters more than the headline. A 256K "pass" here means long prefill plus a coherent opening segment with finite logits — not 256K tokens of validated sustained generation. The validated serving path is batch one; continuous batching at 256K is not proven. A separate speed-focused artifact reached 30.7–35.7 decode tok/s but did not clear the same quality gate, so it did not replace the coherent baseline. A single H100 running the official FP8 checkpoint substantially outperformed the historical Trainium artifact — which is a statement about software-path maturity, not a hardware verdict, and I would not present it as one.

Along the way the work also surfaced a corruption in a shared NKI QKV FP8 context-encoding path: past a 96-token dispatch threshold the CTE sub-kernel produced garbage projections where the token-generation path stayed coherent. The mitigation tiles the sequence to ≤96 tokens and forces the correct kernel. Observed on this model and precision; I've been careful not to claim it generalizes.
