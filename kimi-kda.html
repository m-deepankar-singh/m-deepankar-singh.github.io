What it actually takes to serve Kimi K3 — and what its attention does on hardware you can rent

27 July 2026 · 4× RTX PRO 6000 Blackwell · vLLM 0.25.1 · TP=2 · batch 1

K3's weights drop in a few hours. The self-host guides went up before them. This piece does two things: answers the hosting question with arithmetic and primary sources instead of confidence, and then measures the thing that actually makes K3 interesting — its attention — using the 48B model Moonshot shipped on the same architecture. I did not run K3. Nobody outside a handful of labs has.

1The frame

At least one published guide describes a model that does not exist: 594 GB of weights, 128K context, Apache 2.0, launch with --max-model-len 131072. Against Moonshot's own announcement the context window is 1,048,576 tokens, the license terms are not published at all, and 594 GB is arithmetically impossible — 2.8 trillion parameters at MXFP4's four bits is about 1.4 TB, and 594 GB would imply roughly 1.7 bits per parameter.

That is the state of the coverage: written against a countdown timer, not against weights.

So this piece does two things. First, the hosting question answered with arithmetic and primary sources. Second — because the interesting thing about K3 is not its size but its attention — an actual measurement of that attention mechanism, on named hardware, using the 48B model Moonshot shipped on the same architecture.

Anyone publishing K3 throughput before the weights are public should be asked what they ran it on.

2Part 1 — What you need to serve K3

PlusKV/state cache, activations, and MoE routing overhead on top

Worth being precise about the provenance, because every guide states it as fact. Moonshot's own K3 quickstart page gives the parameter count, the expert counts, the 1M context and the architecture — and states no weight format, no license terms, and no hardware requirements at all. The MXFP4/MXFP8 figure comes from vLLM's integration post. The 1.4 TB above is arithmetic on top of vLLM's number, which means it inherits vLLM's assumption. I would rather say that than round it into a spec.

Moonshot's own deployment guidance is "64 or more accelerators." The eight-node figure circulating in the guides is somebody's gloss, not a vendor number. vLLM's preview post says their validation ran on a 16-GPU DP16 + EP16 configuration.

Why the obvious instances are the wrong instances

H100 has no native FP4. Serving MXFP4 weights there means dequantising to FP8 or BF16, which makes the memory picture worse than the 1.4 TB baseline, not better. At 640 GB per 8×H100 node you are looking at four-plus nodes, for a model whose native format the silicon cannot execute.

Blackwell is the right architecture class — it has native FP4 — but the workstation-class Blackwell parts are not enough of it. Eight RTX PRO 6000 Blackwell Server Edition at 96 GB each is 768 GB, about half the floor. Two such nodes clears the arithmetic and fails the topology: these GPUs talk over GPUDirect P2P on PCIe, not NVLink, with EFA between nodes. An 896-expert MoE with 16 active is an all-to-all-heavy workload, and all-to-all over PCIe is the worst case for it.

That topology limit is not speculative. On the node used for Part 2, vLLM's custom all-reduce kernel crashed outright — custom_all_reduce.cuh:455 'invalid argument' — and both servers had to fall back to NCCL via --disable-custom-all-reduce. That is a two-GPU collective on a single node. Scaling an all-to-all MoE across a PCIe fabric is a harder version of the problem that already broke here.

That leaves NVL-class Blackwell in quantity — which is to say, the 64+ accelerators Moonshot said, which is to say, not a thing you rent on a card.

What the software supports today

From vLLM's own preview post, not from a blog that read it. Integrated: KDA prefill and decode kernels, fine-grained prefix caching for hybrid attention, Attention Residuals kernels, an optimised MLA module for prefill/decode disaggregation, MXFP4 MoE execution via TRTLLM-Gen and DeepGEMM paths, multimodal, tool calling, structured output.

Still in progress at time of writing: KDA prefill backend selection and numerical validation, end-to-end serving semantics validation, disaggregated and offload scenarios, AMD ROCm tuning. No required version is stated. No launch command is published. No throughput number appears anywhere in it.

Also absent, and worth noting if you care about serving economics: no speculative decoding, no MTP, no DFlash path. The tooling around this architecture is younger than the architecture.

The honest summary

You cannot serve K3 on one node of anything currently rentable by the hour. If you have 64+ NVL-class Blackwell accelerators, vLLM has a preview path and is explicit that parts of it are still being validated. If you do not, the practical answer today is an API.

3Part 2 — But you can measure the attention

K3's most consequential design choice is not its parameter count. It is Kimi Delta Attention — a linear-attention mechanism hybridised with periodic full attention. And that is testable, because Moonshot shipped Kimi-Linear-48B-A3B-Instruct: 48B total, 3B active, a 3:1 KDA-to-global-MLA hybrid, MIT, 98.3 GB of BF16 weights across 20 shards. Same mechanism, same ratio, one node.

KDA is described by its authors as extending Gated DeltaNet with a finer-grained gating mechanism. The interesting property of a linear-attention hybrid is never the headline throughput — it is what the shape of the latency curve tells you about where state lives.

What the paper claims, and the part everyone skips

Two headline numbers. Figure 1b: 6.3× faster TPOT — 1.84 ms versus 11.48 ms at 1M tokens — against MLA. Figure 1a: 3.98× acceleration on RULER at 128K, at higher quality (84.3 vs 81.3). The model card rounds 6.3× to 6×.

Credit where due, the baseline is fair: the paper states all compared models use the same 48B/3B setting with the same layer and head counts, so it is a controlled architectural comparison, not a convenient product matchup.

Here is what I could not find in the paper, the repo, or the model card: what hardware any of it ran on. No GPU type, no node count. There is also a wrinkle in the paper's own text — the 6.3× caption attributes part of the gain to enabling larger batches, while Figure 7b states batch size 1 was used.

That is not an accusation. It is a gap, and it is the gap this fills.

4Method

Four NVIDIA RTX PRO 6000 Blackwell Server Edition GPUs on one node: 96 GB GDDR7 each, 1,597 GB/s memory bandwidth, GPUDirect P2P over PCIe, native FP4.

Two vLLM servers, TP=2 each, on disjoint GPU pairs — KDA on GPUs 0,1 and the control on GPUs 2,3 — so both models see the same silicon, driver and kernels. TP=2 rather than TP=4 deliberately: tensor parallelism all-reduces on every decode step, that collective crosses PCIe rather than NVLink here, and TPOT is the exact quantity being measured. Four-way collective traffic would have been measuring the interconnect.

KDAmoonshotai/Kimi-Linear-48B-A3B-Instruct — 48B total / 3B active, 3:1 KDA-to-global-MLA, BF16, 98.3 GB
ControlQwen/Qwen3-30B-A3B-Instruct-2507 — 30.5B total / 3.3B activated, 48 layers, 128 experts with 8 active, GQA with 32 Q heads and 4 KV heads. Conventional full attention.

Matching active parameters — 3.3B against 3B — is the whole point. A 48B-vs-7B comparison measures model size and calls it attention.

Both at --max-model-len 262144 and --disable-custom-all-reduce. That ceiling is the control's native context. It could have been pushed higher with YaRN, but a rope-extended baseline against a natively-1M model is unfair in a direction that happens to flatter the headline.

Prompt sweep at 1K / 4K / 16K / 64K / 128K / 262K, fixed 128-token decode budget, streaming so TTFT is real time-to-first-token, median of three after a discarded warm-up. Batch 1. The two models were swept sequentially, not concurrently, so neither contended with the other for PCIe or host bandwidth. The 262K point uses a prompt of 262,016 tokens, because prompt plus the 128-token output budget has to fit inside max_model_len — the first attempt at a flat 262,144 was rejected with an HTTP 400, correctly.

Three parity details I am not going to bury

The memory-utilisation figures differ, and in the control's favour. KDA runs at --gpu-memory-utilization 0.80, the control at 0.90. This was not a choice; the KDA server OOMs at 0.90 and again at 0.85. vLLM's memory profiler underestimates the KDA recurrent-state allocation — a ~7.38 GiB block lands after the KV budget has already been committed. So the faster model here is the one running on the smaller memory budget. If that biases anything, it biases against the result being reported.

Prefix caching had to be forced off on the control. vLLM auto-disables prefix caching for the hybrid KDA model but leaves it enabled for Qwen. Since the harness sends the same prompt three times per point, the control's second and third repeats would have hit the prefix cache and reported a near-zero TTFT — a silent, entirely invisible rig in the control's favour. The control was relaunched with --no-enable-prefix-caching and both flags were verified in the serve logs before any measurement was taken. This is the single easiest way to accidentally publish a wrong number in this comparison, and I nearly did.

An unrelated process was resident on all four GPUs, holding about 552 MiB per card and idle throughout. It is symmetric across both models and small relative to 96 GB, but it is there, and it is part of why the KDA server needed the lower utilisation ceiling.

The kernel-fallback gate passed. The serve log shows TRITON_MLA for decode and FLASH_ATTN MLA for prefill on the global-attention layers, and no reference, naive or fallback path on the KDA layers. Two warnings are worth stating rather than hiding. SymmMemCommunicator is unsupported at compute capability 12.0, so both models fall back to NCCL — symmetric, no effect on the comparison. And vLLM warns that Kimi ships a slow tokenizer; tokenisation happens inside TTFT, which matters for exactly one data point below.

The bandwidth angle, which is why this is more interesting than an H100

An RTX PRO 6000 Blackwell has 1,597 GB/s of memory bandwidth. An H100 SXM has about 3,350 GB/s of HBM3. Roughly half. (The PCIe H100 is lower, ~2 TB/s; the SXM part is the fair comparison.)

Decode is bandwidth-bound, so ordinarily that is a straightforward penalty. But it should not be an equal penalty. A full-attention model re-reads a KV cache that grows linearly with context, so it pays that bandwidth cost on every token and the cost grows with the prompt. A linear-attention layer carries fixed-size state, so it should barely notice.

Which means lower-bandwidth silicon should widen the gap between the two architectures rather than narrow it — and if that holds, the practical conclusion is the opposite of the usual advice: linear-attention hybrids are the models that tolerate cheap inference silicon.

I have not seen anyone publish that comparison. Here it is.

The number to look at is not the absolute TPOT. It is the slope.

31% vs 150% per-token latency growth across a 256× context increase

Across a 256× increase in context, KDA's per-token latency rises 31% — from 5.28 ms to 6.94 ms. The control's rises 150%, from 5.78 ms to 14.45 ms. Restricted to the more commonly quoted 128K ceiling, it is +11.7% against +73.5%.

That flatness is an architectural signature rather than a speed result. It is what fixed-size recurrent state looks like from the outside: the per-token work stops depending on how much context precedes it, so the curve goes flat and stays flat. The full-attention control has to re-read a cache that grows with every token it has already seen, and its curve shows exactly that.

It also means the headline ratio is not a fixed property of the architecture. It is a function of how much context you actually use. At 1K the two models are within 10% of each other and the attention mechanism is close to irrelevant. Anyone quoting a single speedup number for linear attention without naming a context length is quoting a number about nothing.

At 1,024 tokens the tokeniser is a meaningful fraction of an 81 ms measurement; by 4K the prefill work dominates and the ordering flips permanently. Reporting it as measured rather than quietly starting the table at 4K, but no architectural claim should be read into it.

Did the 6.3× hold up?

The honest answer is that this measurement cannot confirm or refute the paper's 6.3×, and anyone who tells you otherwise is merging two different experiments.

The paper's figure is KDA against MLA at 1M tokens. This one is KDA against GQA at 262K. Different baseline, different context length, different hardware — and the paper does not say what hardware, which is why this piece exists. Three of the four variables differ. Publishing "2.08×, so the 6.3× didn't hold" would be exactly the kind of number-laundering this article was written to complain about.

What this measurement does establish, on its own terms: the ratio grows monotonically with context, from 1.09× at 1K to 2.08× at 262K, with no sign of flattening at the top of the range. The paper's claim is that the gap keeps widening out to 1M. Everything measured up to 262K is consistent with that shape. That is a weaker statement than a replication and it is the strongest one the data supports.

KV cache footprint

This is the one section where the numbers are not mine. vLLM prints its own allocation report at startup, before any benchmark runs, and both servers printed one:

KV memory / GPUCache capacityConcurrency @ 262K
KDA (util 0.80)21.85 GiB2,874,255 tokens10.96×
Control (util 0.90)53.66 GiB1,172,112 tokens4.47×

Read the raw GiB column and you will read it backwards. The control has more cache memory, not less — it ran at 0.90 utilisation against KDA's 0.80, for the reason given above: the KDA server OOMs at anything higher. So the model with the smaller memory budget is the one holding 2.45× more tokens.

The comparable quantity is density — bytes of cache per token of context:

Control: 53.66 GiB × 2 GPUs ÷ 1,172,112 tokens = 96.0 KiB/token
KDA:    21.85 GiB × 2 GPUs ÷ 2,874,255 tokens = 15.9 KiB/token
6.0× more context per byte of cache — from the server's own accounting

The control's figure is worth a second look, because it is checkable from the model card alone. Qwen3-30B-A3B is 48 layers with 4 KV heads of 128 dimensions, at 2 bytes for BF16, times 2 for K and V:

2 × 48 layers × 4 KV heads × 128 dim × 2 bytes = 98,304 bytes = 96 KiB per token
vLLM measured 96.01.

That arithmetic and that allocator agree to within a rounding error, which is the best evidence available that the density frame is the right one and that neither number is an artefact of how the servers were configured.

One thing I will not claim from this. Moonshot's stated memory figure is a reduction of up to 75% during long-sequence generation, and 6× density is an 83% reduction — but those are not the same measurement and the larger number is not a beat. Moonshot's 75% is the ceiling implied by the 3:1 hybrid ratio within the same model family, KDA hybrid against full MLA at identical config. This is KDA against a different model's GQA, and GQA with 4 KV heads is simply a fatter cache than MLA. The two figures measure different comparisons and should not be set against each other.

Context ceiling

Both models reached 262K. The control allocated and served its full native 262,144-token context without difficulty, so there is no capability asymmetry to report — the 2.08× is measured at the control's own maximum, on equal footing, which is the cleaner result anyway.

Stating this explicitly because the tempting version of this section is the one where the baseline falls over and the story writes itself. It didn't. Qwen3-30B-A3B served 262K fine.

One thing that is not a benchmark result but is worth your time

Serving a hybrid-attention model is rougher around the edges than serving a GQA model. The KDA server OOM'd twice at utilisation settings the control handled without complaint, because vLLM's profiler does not yet account for the recurrent-state allocation. The custom all-reduce kernel crashed on this topology. The tokenizer is slow enough to be visible in short-context TTFT. None of this is fatal and all of it is fixable, but if you are budgeting time to bring one of these up, budget more than you would for a conventional model. The architecture is ahead of its tooling.

6What this does and does not say about K3

It says: the attention mechanism K3 is built on produces, on independent named hardware, a decode curve that is nearly flat where a conventional one is not — 31% latency growth against 150% over a 256× context increase — and that this is real and reproducible outside the lab that shipped it.

It does not say anything about K3's own numbers. I did not run K3.

The honest version of the connection is architectural: if you want to know whether K3's long-context serving story is credible before you commit to 64+ accelerators, the 48B model in the same family, on one node, will tell you more than any spec sheet — and more than any guide written against a countdown timer.

When the weights actually open, the follow-up writes itself: publish K3's real config.json against what the guides claimed it would be. That is a measurement anyone can make. K3 throughput is not.

7What is not validated

  • Batch 1 only. No concurrency claim.
  • Control is GQA full attention, not MLA. The paper's comparisons use MLA. The two numbers are not comparable and are not compared here.
  • Sweep tops out at 262K, bounded by the control's native context. The paper's 6.3× is at 1M.
  • The two servers ran at different --gpu-memory-utilization (0.80 KDA, 0.90 control) because the KDA server OOMs above 0.80. Disclosed above; it disadvantages the model that won.
  • An idle unrelated process held ~552 MiB on each GPU throughout, symmetric across both models.
  • The KV-cache density figures assume vLLM's per-worker Available KV cache memory line reports per-GPU memory, doubled for TP=2. The control's result matching its config-derived 96 KiB/token to within 0.01 KiB is the check on that assumption.
  • The 6× density figure is KDA against GQA, not against MLA, and is therefore not comparable to Moonshot's own "up to 75%" claim, which is a within-family MLA comparison.
  • Quality was not evaluated. This measures serving behaviour, not model output.
  • No K3 measurements of any kind appear in this article.
  • K3 figures come from Moonshot's announcement and vLLM's preview post, not from weights. The 1.4 TB is derived arithmetic, not a published size. Moonshot has not published license terms; anyone telling you K3 is Apache 2.0 or MIT today is guessing.
  • The H100 bandwidth figure used for comparison is a published spec, not a measurement — no H100 was run.
  • One node, one set of software versions, on 27 July 2026.
